LAB: FILE PATH TRAVERSAL, TRAVERSAL SEQUENCES STRIPPED NON-RECURSIVELY

Autor: David Campos Morado - 183511 | Ingeniería en Tecnologías de la Información
Profesor: Servando Lopez Contreras

Objetivo del Laboratorio

Identificar y explotar una vulnerabilidad de File Path Traversal evadiendo un mecanismo de defensa no recursivo[cite: 58]. El objetivo es obtener acceso y leer el archivo /etc/passwd manipulando la carga de imágenes[cite: 58].

Marco Teórico

File Path Traversal: Es una vulnerabilidad que permite a un atacante acceder a archivos y directorios almacenados fuera del directorio raíz web de la aplicación[cite: 58, 59].

Filtro No Recursivo: Algunos entornos o servidores web implementan filtros que eliminan de forma automática las secuencias obvias de path traversal, como ../[cite: 59]. Sin embargo, si este proceso de eliminación no es recursivo (es decir, el filtro se aplica solo una vez), un atacante puede crear secuencias anidadas (como ....// o ..././). Cuando el filtro elimina la secuencia central detectada, los caracteres restantes se unen formando un nuevo ../ válido, evadiendo así la restricción original[cite: 59]. Adicionalmente, el filtro puede fallar si la codificación de la URL no es estándar[cite: 60].

Desarrollo de la Práctica (Procedimiento y Evidencias)

Paso 1: Análisis del entorno y objetivo
Se inició accediendo al laboratorio en Web Security Academy para comprender el contexto: la aplicación elimina de forma no recursiva las secuencias de salto de directorio[cite: 57]. El objetivo es leer /etc/passwd[cite: 57].

[ FIGURA 1: Análisis del objetivo en Web Security Academy. ]

Paso 2: Preparación e Intercepción con Burp Suite
Se inició Burp Suite y se navegó por el sitio de la tienda con el proxy activado. Se interceptó una petición GET que solicitaba una imagen a través del parámetro filename y se envió al módulo Repeater para su posterior análisis[cite: 61].

[ FIGURA 2: Captura del tráfico HTTP en el Repeater mostrando la petición GET al endpoint /image. ]

Paso 3: Explotación del Filtro No Recursivo
Sabiendo que el servidor elimina secuencias ../ pero no lo hace de manera recursiva, se diseñó un payload anidado. En lugar de usar ../../../etc/passwd, se utilizó ....//....//....//etc/passwd[cite: 61].

Explicación del Payload y Resultados

Análisis del Payload:

GET /image?filename=....//....//....//etc/passwd HTTP/2
  • El payload aprovecha la debilidad del filtro no recursivo[cite: 61].
  • Cuando el servidor procesa ....//, detecta y elimina la secuencia interior ../[cite: 61].
  • Los caracteres que quedan (el primer punto, el último punto y la barra final) se concatenan para formar un nuevo y válido ../, logrando el salto de directorio esperado[cite: 61].

Resultados Obtenidos:

  • Al enviar la petición modificada, el servidor devolvió un HTTP/2 200 OK[cite: 61].
  • La respuesta expuso el contenido completo del archivo /etc/passwd[cite: 61].
  • Esto confirma que el filtro no recursivo fue exitosamente evadido, permitiendo acceder a archivos críticos del sistema[cite: 61].
[ FIGURA 3: Respuesta del servidor mostrando el archivo /etc/passwd tras la evasión del filtro. ]

Mitigación Recomendada

Para prevenir esta vulnerabilidad, se recomienda no pasar entradas proporcionadas por el usuario a las API del sistema de archivos. Si es absolutamente necesario, la aplicación debe normalizar la entrada antes de validarla, resolviendo todas las secuencias relativas (como ../) y asegurando que la ruta resultante resida dentro de un directorio base autorizado (por ejemplo, usando funciones como realpath()).
